# 技术书籍章节评审

对技术书稿章节做发布前评审。核心原则：**先取证，再打分**。任何结论都必须有证据支撑——代码要真跑，技术表述要对照官方文档/源码，数字要能追溯。禁止只凭阅读印象给分。

本书写作规范见仓库根 `AGENTS.md`（场景→问题→实现→原理→最佳实践→排障→面试题→小结；源码≤30%；SVG 图；生产案例）。评审时把它当作硬性标准之一。

## 工作流

### 1. 定位与摸底
- 读被评审的 `.md` 章节全文。
- 找到配套代码目录（本书约定：`NN-章节名.md` 对应同级 `NN-xxx/` 目录，独立 go.mod）。
- 读 `outline.md` 判断哪些主题属于本章、哪些应留给后续章节（完整性打分要区分"缺失"和"故意后置"）。

### 2. 逐维度取证
对每个维度，**先收集证据再下判断**。证据类型和取证手段见下方「八个维度」。典型取证动作：
- 代码：`gofmt -l .`、`go vet ./...`、`go build ./...`（能连服务就跑 `go test ./...`）。逐个 example 检查错误处理、固定 key 是否清理、输出是否可复现。
- 技术表述：对照官方文档或本地依赖源码（`go env GOMODCACHE` 下的库源码）核实版本相关行为（编码格式、默认参数、结构体字段语义等）。
- 数字/性能结论：查是否标注来源与版本；无据的软化或加引用。

### 3. 打分与结论
- 每个维度 1-10 分，**必须附一句评审结论 + 具体证据**（文件:行号 / 命令输出 / 文档链接）。
- 综合评分 = 八维度加权或均值（默认均值），给出是否达到发布标准的结论。
- 输出「优先整改清单」：按 正确性 > 可验证性 > 可追溯性/可引用性 > 其他 排序，每条给出 `文件:行号` 和修法。

### 4.（可选）执行整改
若用户要求整改：逐条修，改完重跑 `gofmt -l . && go vet ./... && go build ./...` 验证，再复述改动对应了哪些评审项。

## 八个维度

评审严格程度：技术书稿面向付费读者和后续维护者，**宁严勿松**。会误导读者的表述即使"大方向对"也判正确性失分。

### 1. 正确性（correctness）
技术表述是否准确、代码语义是否成立。高风险点：
- 版本相关行为（如 Redis 7 用 listpack 而非 ziplist；某字段在新版语义变化）。
- "简化表述"越过准确性边界（如把单实例强一致说成"最终一致"）。
- 示例代码语义不成立（如 `SDIFF` 单 key、`ZRANGEBYSCORE` 缺 `Min`、库指标字段用错）。
- **取证**：对照官方文档 + 依赖源码，不靠记忆。

### 2. 完整性（completeness）
章节框架是否齐全（对本书=AGENTS.md 的八段模板），面向生产的必要边界是否交代。
- 区分"真缺失"与"大纲后置"：查 `outline.md`，若无后续章节承接则算缺失。
- **取证**：逐段核对模板；列出缺失的生产边界（如持久化/高可用/安全/监控）。

### 3. 一致性（consistency）
前后标准是否统一、示例命名与正文是否一致、正文主张与示例是否矛盾（如"必须设过期时间"却示例用永久 key）。

### 4. 可验证性（verifiability）
代码能否真跑、结果能否复现。
- **取证**：实际执行 `gofmt`/`vet`/`build`/`test`。检查固定 key 多次运行是否积累脏数据、错误是否被吞。这一维度**不跑不给分**。

### 5. 可追溯性（traceability）
版本、命令行为、性能数字、内部实现是否有来源可查。无据的"微秒级""每秒 N 次"等要扣分。

### 6. 可维护性（maintainability）
独立 module、环境变量、分目录等结构是否利于扩展；重复代码、散落常量、缺错误处理是否推高后续维护成本。

### 7. 可理解性（comprehensibility）
从真实场景切入是否自然、图示是否帮助建立概念、推进是否顺畅。注意"简化"与"不准确"的边界。

### 8. 可引用性（citability）
是否有参考资料、脚注、官方文档链接、版本依据、延伸阅读。作为书稿，读者和维护者要能核验关键结论。缺引用是硬伤。

## 输出格式

```
| 维度 | 得分 | 评审结论（附证据） |
|------|------|------|
| 正确性 | N | ... 具体到 文件:行号 |
| 完整性 | N | ... |
| 一致性 | N | ... |
| 可验证性 | N | ... 附命令输出 |
| 可追溯性 | N | ... |
| 可维护性 | N | ... |
| 可理解性 | N | ... |
| 可引用性 | N | ... |

综合评分：X.X / 10
结论：<是否达到发布标准 + 优先整改方向>

## 优先整改清单
1. [正确性] 文件:行号 — 问题 → 修法
2. [可验证性] ...
```

## 硬规则
- 不跑代码不给可验证性分；不查文档不给正确性/可追溯性的"通过"结论。
- 每个扣分点都要能指到 `文件:行号` 或给出命令输出/文档链接，不写空泛评语。
- 打分从严：会误导读者 = 正确性重扣；无引用 = 可引用性重扣。
